Laboratorio 0

Primer contacto

Dos rutas

Constructores api/

  1. Abre reservas-farmacia/api en Kiro IDE y confía en el workspace.
  2. Pide: "Explica la arquitectura de este proyecto y cómo correr los tests".
  3. Pide: "Corre los tests" y aprueba el comando.
  4. Recorre el panel de Kiro: Specs, Agent Hooks, Steering & Skills y MCP.
  5. Da contexto con #file y #codebase; ubica el modo Vibe/Spec y el selector de modelo.

Negocio negocio/

  1. Abre la carpeta reservas-farmacia en Kiro IDE.
  2. Pide: "Resume en 5 viñetas el problema de negocio descrito en negocio/".
  3. Pide: "¿Qué preguntas le harías a operaciones antes de construir esto?"
  4. Señala un documento con #file:negocio/politicas-retiro.md.
Éxito

Constructores: los tests base pasan. Negocio: un resumen correcto y al menos 3 preguntas útiles.

SoftwareOne · Kiro
Si algún test falla, revisar que se haya corrido npm install. Hay un test marcado como pendiente (skip): es intencional. Context providers: escribir # en el chat (#file, #codebase, #terminal, #git diff, #url, #spec). Selector de modelo en Auto; cada pedido consume créditos.

02 · De la necesidad al plan
Specs

Antes de escribir código, acordar qué es "terminado"

requirements.md

Historias de usuario y criterios de aceptación en EARS.

→

design.md

Arquitectura, modelo de datos, diagramas y estrategia de pruebas.

→

tasks.md

Tareas discretas que el agente ejecuta y marca, en olas paralelas.

FORMATO EARS

WHEN una reserva cumple 24 horas sin ser retirada
THE SYSTEM SHALL marcarla como vencida y liberar el stock reservado

Cada requisito se puede probar con un sí o un no, y se puede rastrear hasta la tarea y el código que lo implementa.

Fuente: kiro.dev/docs · Specs · Feature Specs

02 · De la necesidad al plan
Laboratorio 1

Reservas que expiran a las 24 horas

En relevo

Negocio Requisitos

  1. Specs → + → Feature → Requirements-First, con el prompt de la necesidad.
  2. Revisa cada requisito: ¿se prueba con un sí o un no?
  3. Ejecuta Analyze Requirements y decide cada ambigüedad: horarios, feriados, recetas.
  4. Escribe 2 requisitos propios en EARS y pásalos a tu pareja.

Constructores Diseño y tareas

  1. Con los requisitos de tu pareja, genera design.md y revisa modelo, endpoints y pruebas.
  2. Genera tasks.md y elige Run all tasks; observa las olas paralelas.
  3. Corre los tests.
Éxito

Los tres archivos de la spec existen, todas las tareas están completas y los tests nuevos pasan.

Prompt: "Una reserva sin retirar expira a las 24 horas y libera el stock. El cliente elige el local de retiro y recibe un aviso cuando está lista. Operaciones puede listar las reservas vencidas por local". Reto L200: Design-First y Quick Spec. Reto L300: Bugfix Spec del error de PATCH /reservas/:id. SoftwareOne
04 · Reglas automáticas
Hooks

Cada vez que pasa algo, el agente reacciona

Disparador

PostFileSave, PreToolUse, PostToolUse, Prompt Submit, Agent Stop, Post Task Execution o manual, con un botón.

→

Filtro

Patrón de archivo o de herramienta: \.(ts|tsx)$, read, shell, @mcp.

→

Acción

command: un comando en el proyecto. agent: una instrucción al agente.

Feedback rápido

Lint y pruebas tras cada archivo que edita el agente.

Guardarraíl

En PreToolUse, una salida distinta de cero bloquea la herramienta.

Kiroignore

Deja secretos y archivos sensibles fuera del alcance del agente.

Fuente: kiro.dev/docs · Hooks · Hook actions · Kiroignore
Los hooks viven en .kiro/hooks/*.json. Los de archivo solo reaccionan a cambios del agente, no a ediciones manuales. Las acciones command no consumen créditos; las agent sí.

SoftwareOne
05 · Conectar y estandarizar
Extender al agente

Herramientas, procedimientos o ambos

MCP

Herramientas externas

Servidores locales o remotos (url). Por proyecto en .kiro/settings/mcp.json o por usuario; autoApprove afina permisos.

Skill

Procedimientos

Un SKILL.md con instrucciones, scripts y referencias. Solo carga el nombre y la descripción hasta que se necesita.

Power

Paquete completo

Una carpeta con POWER.md, MCP y steering. Se activa por palabras clave de la conversación.

¿Por qué no conectar todo?

Cinco servidores MCP pueden cargar más de 100 herramientas antes del primer pedido y saturar el contexto. Skills y powers cargan solo lo relevante para la tarea.

Fuente: kiro.dev/docs · MCP · Agent Skills · Powers

06 · Orquestar trabajo de varios pasos
Workflows

Se describe el resultado; Kiro arma el proceso

Paso

Un agente en su propia sesión, con contexto enfocado.

Entrega

Un paso pasa evidencia al siguiente: informe, plan, resultado.

Ramas

Revisores independientes evalúan el mismo trabajo.

Ciclo

Se repite hasta que se verifica o hasta el tope de intentos.

Investigar

Informe con citas.

→

Planear

Plan de cambios.

→

Implementar

Código, intento a intento.

↺

Verificar

Pruebas y revisión: si no pasa, vuelve.

Corre en segundo plano y usa más tokens que un chat. Para algo corto bastan los subagentes, en paralelo.

Fuente: kiro.dev/docs · Workflows
Se activa en Workspace Configuration → Workflows. Recetas incluidas: investigate (solo lectura), feature-pipeline (entrega completa) y publish-pr. Las recetas propias se guardan en .kiro/workflows/. Se puede pausar, retomar o escribirle a un paso. Subagentes: reparten trabajo en paralelo y devuelven el resultado en el mismo turno; el workflow conviene cuando la estructura y la revisión valen el costo.

07 · El agente trabaja solo
Agentes y automatización

Un rol, unas herramientas y unos límites

Custom agent

.kiro/agents/reviewer.json

  • tools: qué herramientas puede usar
  • resources: steering y skills que carga
  • permissions: qué comandos se aprueban solos
  • prompt: su rol e instrucciones
Headless

Sin nadie frente a la pantalla

  • kiro-cli chat --no-interactive
  • Autenticación con KIRO_API_KEY
  • --trust-tools con IDs exactos
  • Salida en JSON Lines para scripts y CI
  • Antes, en modo interactivo: /tools muestra los IDs

Se confía en los límites, no en el agente: permisos acotados, hooks que bloquean y revisión humana del resultado.

Fuente: kiro.dev/docs · Custom agents · Headless mode
El modo headless requiere planes Pro, Pro+, Pro Max o Power, o que el administrador habilite las API keys. Preferir --trust-tools sobre --trust-all-tools.

Para llevarse

Cinco ideas para la próxima semana

  • Pasar de escribir el software a diseñar el entorno con el que el agente lo escribe.
  • La ejecución se abarató; la dirección es lo que vale: requisitos y contexto primero.
  • Las primeras semanas se sienten más lentas; después la ganancia se acumula.
  • Se confía en los límites, no en el agente.
  • Empezar con un equipo y una funcionalidad acotada, y comparar el resultado.
